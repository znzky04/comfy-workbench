# 两个工程决策案例

更新：2026-10-26。对应当前源码和已有测试；这里区分设计选择、实际覆盖与限制。

公开准备补充：提交批次现在在每次获得远端 ID 后立即保存 ID 与实际参数。
中途失败继续观察已接受任务，保存其输出并将批次判为失败；进程在提交中退出时不自动补交。
该保护仍不能消除远端已接受、但本地尚未收到响应/落盘的窗口，不能声称恰好一次提交。
证据见 `tests/test_submission_recovery.py` 的第二次提交失败、进程中断、重载观察与 wait 路径。

## 1. 用工作流注册表与哈希识别版本漂移

**问题。** 多个入口各自保存工作流时，相同名称可能指向不同节点图；参数映射仍可运行，却不再对应当时记录的版本。

**选择。** 5 条 API 工作流登记稳定 ID、版本、SHA-256、参数绑定和输出节点。`WorkflowRegistry.validate()` 校验文件内容哈希与绑定位置；`prepare()` 先校验，再在深拷贝上写入参数。任务 manifest 保存所选工作流版本与哈希，原始 API 文件保持不变。

**代价。** 工作流修改后必须同步维护注册表、哈希和映射。哈希只能识别内容变化，不能判断模型质量，也不能证明远端插件已经加载了相同版本。DSH 预设需要单独导入与参数契约验证。

**证据。** `src/comfyui_agent_studio/registry.py`；`tests/test_registry.py` 中的静态校验、seed 0、HQ 参数镜像测试。`examples/offline_review.py` 会在隔离临时目录修改示例图，验证哈希校验能够发现变化，不触碰正式工作流。

## 2. 持久化任务身份，重启后查询而非重复提交

**问题。** 本地网页关闭后，ComfyUI 中的任务仍可能运行。仅依靠网页内存保存队列，会在重启后丢失任务身份，并可能再次提交同一个请求。

**选择。** 任务记录持久化 `job_id`、远端 `prompt_ids` 和状态历史。`ManifestStore.save()` 通过临时文件加 `os.replace()` 写入；新服务实例读取 manifest，`GenerationService.refresh()` 查询历史和队列来更新状态，不重新提交。观察超时只记录失败，不中断整个 ComfyUI 服务；部分已完成输出先保留。

**代价。** 当前使用本地文件存储，没有数据库事务或跨机器协调。临时文件替换减少半写记录，不代表跨文件事务或任意断电下的数据耐久性。恢复依赖远端仍能查询到任务；超时后任务也可能继续执行。

**证据。** `src/comfyui_agent_studio/manifests.py`、`service.py`；`tests/test_job_refresh.py` 覆盖重启查询、远端错误、超时不取消、任务取消幂等与部分输出保留。相关测试使用替身后端，不能替代真实 GPU 验收。离线示例只演示 manifest 重载和状态约束。
